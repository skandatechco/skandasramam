### The server-side updater (gate 0.5)

This repository **never writes** `pooja_days`: the calendar and booking code only `select` from it with the service-role key, and
the Prokerala integration in the repo only fetches and caches in memory. The process that wrote your 7 rows (`source_provider`,
`fetched_at`) lives **outside** this repo, so I cannot test it. Step A removes write access for `anon`/`authenticated` only. The service role
bypasses RLS and keeps all its privileges (proved by step B4 and by tests), so an updater that uses the **service-role key** (or the database
owner / `postgres` role) is unaffected. An updater that writes with the **anon key** would break, and it should: that means the table is writable by anyone.
Find out which it is (read-only):

```sql
select source_provider, count(*), min(fetched_at), max(fetched_at) from public.pooja_days group by 1;
select jobid, jobname, schedule, left(command, 300) as command from cron.job;     -- errors if pg_cron is not installed: fine
select extname from pg_extension order by 1;
```

and look in Dashboard > **Edge Functions**, **Database > Webhooks / Triggers / Cron**, and the project (or host) that holds the Prokerala
credentials. Answer: _what writes pooja_days, and with which key?_ If it is the service-role key or you do not run one: go ahead. If it uses the anon key: stop; it must be moved to the service-role key first.
